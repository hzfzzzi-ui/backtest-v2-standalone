## Context

当前仓库已经具备三类与移动端相关的基础能力：一是桌面研究平台可稳定产出实验、执行预览与市场快照；二是手机端已有私网访问和只读信号看板；三是 `outputs/execution/` 已经存在执行预览结果文件，可以复用为“下一次执行建议”的只读来源。缺少的是面向真实操作的写侧能力，也就是“确认、驳回、改单数量、回写执行状态、留存审计”的协同层。

本次设计面对的主要约束如下：

- 用户明确要求手机端只做半自动交易入口，电脑端保留研究与实际执行权。
- 每笔移动端操作都需要二次确认，且必须可审计、可回放、可解释。
- 手机端未来希望安装为 PWA，但同时不能暴露公网域名，因此必须支持私有 HTTPS 部署，而不是公网域名发布。
- 现有系统更偏“产物驱动”，即实验、执行预览、市场快照都以文件和固定协议落地；新设计应优先复用这种模式，避免立即引入更重的账户/订单中心。

## Goals / Non-Goals

**Goals:**

- 在现有只读移动看板之上，增加手机端确认、驳回、改单数量能力。
- 保持“研究产物是读模型，移动确认是写模型”这两个边界分离。
- 定义桌面执行器与手机端之间的待执行清单、执行状态、审计日志协议。
- 引入逐笔二次确认和显式风控拦截机制，避免手机端把信号直接变成不可审计的执行动作。
- 为未来私有 HTTPS + PWA 安装准备前端入口、部署要求与降级策略。
- 为通知与每日复盘留出结构化产物接口，避免后续继续堆字符串文案。

**Non-Goals:**

- 本轮不设计手机端直连券商，也不把手机端变成最终执行端。
- 本轮不重做桌面研究平台，不把参数编辑、回测运行搬到手机端。
- 本轮不引入面向多用户的完整账户系统、角色权限系统或公网 OAuth。
- 本轮不承诺公网可访问的安装体验，PWA 只面向私有网络内的安全上下文。

## Decisions

### 决策 1：保留“桌面执行权”，手机端只产出 `approval ticket`

- 选择：手机端只能对建议动作执行确认、驳回、改单数量，并生成 `approval ticket`；桌面执行器消费这些 ticket 后才会进入真正执行阶段。
- 不选：手机端确认后直接驱动券商接口或直接提交真实订单。
- 原因：
  - 这满足用户的“半自动下单”边界，同时保留桌面端作为最终执行与风控闸门。
  - 手机端网络环境、PWA 生命周期和浏览器权限都不适合作为最终执行点。
  - 读写解耦后，即使手机端暂时离线或刷新，也不会影响桌面研究和执行通路。

### 决策 2：新增 `outputs/mobile_ops/` 作为移动端写模型目录，采用 append-only 事件协议

- 选择：在 `outputs/mobile_ops/` 下新增结构化产物：
  - `approval_tickets/`：待执行清单
  - `execution_events/`：执行状态事件流
  - `audit_log.jsonl`：逐笔操作审计日志
  - `daily_briefings/`：日终摘要
- 不选：直接把移动端操作写回实验目录，或者立即引入新的订单数据库。
- 原因：
  - 实验目录代表研究产物，不应混入运行时操作状态。
  - append-only 事件流更适合逐笔审计、回放和失败恢复。
  - 当前仓库已经以产物目录为核心组织方式，这种方案与现有结构最一致。

### 决策 3：用“信号快照 + approval ticket + execution event”三段状态机表达移动端交易协同

- 选择：引入明确状态机：
  - `signal_snapshot`: 来自最新实验与执行预览的只读建议
  - `approval_ticket`: 用户确认后产生的待执行指令
  - `execution_event`: 桌面执行器回写的状态变化
- 不选：在同一个对象里混合“建议状态”和“执行状态”。
- 原因：
  - 信号建议和执行结果属于不同事实，混在一起会污染审计语义。
  - 手机端需要同时看到“系统建议什么”和“我已经确认/执行到哪一步”，分层后更清晰。
  - 后续通知和复盘都可以围绕 `execution_event` 聚合，不必重新解析 UI 状态。

### 决策 4：逐笔二次确认不是 UI 文案，而是协议层硬要求

- 选择：任何“确认下发”类动作都必须经历二次确认，后端只接受带 `confirm_token` 或二次确认标记的最终提交。
- 不选：只在前端弹窗提醒，但服务端直接接受单次请求。
- 原因：
  - 用户已明确把二次确认作为核心风控需求。
  - 单纯前端弹窗不能防止误触、重复提交或脚本直接调用接口。
  - 协议层强制能保证未来即使更换前端实现，也不会绕过风控。

### 决策 5：PWA 仅面向私有 HTTPS 正式部署；私有 HTTP 只保留浏览器模式

- 选择：
  - 正式安装模式要求私有 HTTPS 域名或私有证书。
  - `localhost` 仍可用作开发例外。
  - 当访问来源是非安全上下文的私有 HTTP 时，只提供浏览器模式，不展示安装引导。
- 不选：继续要求手机端长期使用纯 HTTP 同时追求完整 PWA 安装能力。
- 原因：
  - 浏览器对 Service Worker 与 PWA 安装能力有安全上下文要求。
  - 用户要求的是“不暴露公网域名”，不是“不能使用 HTTPS”。
  - 私有 HTTPS 才能让未来通知、离线壳、安装入口具备稳定基础。

### 决策 6：通知与日终复盘统一由结构化摘要驱动，不直接拼接 UI 文案

- 选择：后端生成结构化摘要对象，再按渠道映射为站内消息、PWA 提醒或日终卡片。
- 不选：不同渠道各自拼接字符串，彼此语义不一致。
- 原因：
  - 用户优先级里同时包含通知、成交回写、每日复盘，这三者本质上都依赖同一批执行事件与持仓变化。
  - 结构化摘要更容易做测试、可观测和多渠道扩展。
  - 这也符合项目“配置唯一真相、产物可验证”的工程原则。

## Risks / Trade-offs

- [移动端新增写侧能力会提升误操作风险] → 通过逐笔二次确认、幂等 ticket id、桌面端最终执行权和 audit log 降低风险。
- [append-only 文件协议在并发写入时可能出现竞争] → 初期限定单用户/单操作员场景，并要求写入端使用原子写和单文件锁；若未来并发增加，再迁移到数据库。
- [执行回写依赖桌面执行器配合，若执行器未消费 ticket，手机端会出现“已确认但未执行”] → 增加 ticket 超时状态、异常提醒和手工撤销路径。
- [私有 HTTPS 部署会提高局域网安装复杂度] → 先保留私有 HTTP 浏览器模式，PWA 安装作为可选增强而非第一阶段阻塞项。
- [通知能力容易演化成新的消息系统] → 第一阶段只支持少量固定事件：待确认、执行异常、收盘摘要，不扩展成通用消息平台。

## Migration Plan

1. 先保留当前只读移动看板接口与页面，作为 `signal_snapshot` 读模型基础。
2. 新增 `outputs/mobile_ops/` 协议与相关后端接口，但默认不开启自动执行。
3. 先实现 `approval ticket` 的创建、查询、撤回与二次确认，再接入桌面执行器消费。
4. 在桌面执行器接入后再增加 `execution_event` 回写与手机端状态页。
5. 最后补私有 HTTPS、manifest、service worker 与 PWA 安装说明。
6. 如需回滚，可依次关闭：
   - 移动端确认入口
   - 桌面执行器 ticket 消费
   - PWA 安装入口
   当前只读移动看板与桌面研究平台可独立保留。

## Open Questions

- `approval ticket` 是否需要支持“部分确认”，例如只确认候选列表中的部分股票，而不是整批确认。
- 桌面执行器是读取 `approval_tickets/` 文件夹轮询消费，还是通过新 API 拉取待执行指令，哪种方式更符合你实际交易流程。
- 执行状态回写是否需要细分到“已报/部成/已成/已撤/失败”，还是先以更粗的四态实现。
- 通知优先走哪条通道：PWA 推送、Telegram、还是仅站内提醒。
- 每日复盘摘要是否只面向移动端展示，还是要同步沉淀到研究平台和 `outputs/ops/` 目录。
