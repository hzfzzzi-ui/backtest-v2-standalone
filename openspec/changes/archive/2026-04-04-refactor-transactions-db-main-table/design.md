## Context

当前 `mobile_ops` 已经通过统一生命周期服务收住审批、执行和摘要读取，但底层持久化仍以文件域为主，数据库中的 `transactions` 还不是正式的生命周期主表。这造成事务域文档、移动端读取面和执行推进路径之间存在“正式数据库真相”与“文件兼容真相”并存的问题。

## Goals / Non-Goals

**Goals:**
- 把 `transactions` 提升为业务事务域中的正式生命周期主表。
- 固定生命周期状态、账户/标的关联、成交字段、审批来源痕迹、失败原因字段。
- 让移动端审批、执行跟踪、每日摘要优先读取数据库事务真相。
- 保留迁移期 compat 文件写出与回退路径。

**Non-Goals:**
- 不在本 change 中引入通知系统。
- 不在本 change 中重写移动端 UI。
- 不在本 change 中修改研究逻辑、执行时点或前端结果口径。

## Decisions

- 决策 1：以 `transactions` 为完整生命周期主表，而不是继续扩展 `approval_tickets` / `execution_events` 从表。
  原因：文档已经明确事务域要以生命周期主表承接审批、执行、成交、拒绝、撤销等正式真相，继续拆散会延长兼容期。

- 决策 2：保留 compat 文件双写，但将其降级为迁移壳。
  原因：移动端和历史工具链仍可能依赖文件结构，直接删除风险过高；先降级主读取路径更稳。

- 决策 3：每日摘要只消费事务生命周期摘要，不再把 briefing 文件本身当底层真相。
  原因：摘要是事务真相的投影，而不是另一份正式源。

- 决策 4：数据库事务主表字段先锁生命周期状态、账户/标的关联、成交字段、审批来源痕迹、失败原因。
  原因：这些字段是后续事务域完全数据库化的最小闭环。

## Risks / Trade-offs

- [风险] 数据库主表与 compat 文件双写不一致
  → 缓解：设计中要求双写期间固定审计回显和回退读取策略。

- [风险] 旧移动端读取逻辑仍隐式依赖文件路径
  → 缓解：在 specs 中明确正式读取路径切换顺序和 compat 退出条件。

- [风险] 事务生命周期主表过早承诺过多字段
  → 缓解：本 change 只锁最小正式字段，扩展字段留待后续事务域增强。

## Migration Plan

1. 定义 `transactions-lifecycle-main-table` 正式能力与最小字段。
2. 修改移动端审批、执行跟踪、每日摘要 specs，使其正式依赖事务生命周期主表。
3. 保留 compat 文件写出，明确仅为迁移期用途。
4. 在实现阶段先做数据库主表写入与读取，再逐步移除文件主读取面。

## Open Questions

- 数据库主表最终采用单表扩展还是主表 + 状态历史表的组合，留待实现阶段定库表设计。
- compat 文件退出的最终时点，需要与移动端前端重构批次联动确认。
