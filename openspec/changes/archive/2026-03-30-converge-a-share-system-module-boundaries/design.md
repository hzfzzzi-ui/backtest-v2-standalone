## Context

当前仓库已经完成一轮文档重整，正式把系统分成：

- 组合总控
- A 股个股子系统
- ETF 子系统
- 执行内核
- 正式记账与正式审计
- 研究诊断层
- 研究拼接层

但当前代码现实仍然存在边界混层：

- 组合总控仍会间接塑造 ETF 子系统内部行为
- 子系统会向执行内核暴露中间预算、节奏和诊断字段
- 执行内核会直接感知部分策略私有语义
- 研究诊断与正式产物仍共享部分未分层的语义

这会带来三个直接问题：

1. 代码实现容易偏离新架构文档
2. 后续 L3 改动难以归因、回滚和验证
3. 多资产扩展时，新的子系统会继续污染共享层

## Goals / Non-Goals

**Goals:**

- 以最新架构文档为锚点，定义正式模块职责与正式边界
- 让组合总控回到组合级风险与预算控制层
- 让个股子系统与 ETF 子系统都通过统一最终目标持仓合同接入执行内核
- 让执行内核只处理共享执行规则，而不消费子系统私有语义
- 让正式审计与研究诊断形成清晰分层

**Non-Goals:**

- 不调整 A 股个股正式策略口径
- 不调整 ETF 正式策略口径
- 不扩展新的资产范围
- 不直接做收益优化
- 不在本 change 中一次性完成所有历史代码清理

## Decisions

### 决策 1：以“组合总控 -> 子系统 -> 执行内核 -> 正式审计”作为唯一正式主链

理由：

- 这是当前文档已经明确锚定的正式结构
- 这条链能把组合级风险控制与子系统内部逻辑拆开
- 这也是未来多资产扩展最稳的边界

备选方案：

- 继续允许组合总控、子系统、执行内核之间共享部分中间语义

不采用原因：

- 会继续制造多套真相
- 无法从架构层约束后续实现偏移

### 决策 2：组合总控只保留组合级正式职责

组合总控只定义：

- 风险环境
- 总预算边界
- 子系统预算上限
- 硬阻断
- 防守倾向

理由：

- 这些是组合级控制层职责
- 再向下就是子系统内部语义

备选方案：

- 继续让组合总控理解 ETF 的内部模板、节奏和恢复语义

不采用原因：

- 会让共享层持续被 ETF 私有逻辑污染
- 后续接入其他资产时会继续复制这种耦合

### 决策 3：子系统对执行内核只暴露“最终目标持仓合同”

正式子系统输出统一收敛为：

- 决策日期
- 执行日期
- 标的列表
- 每个标的目标权重
- 原因摘要
- 组合级阻断结果

理由：

- 执行内核的唯一职责是把目标持仓转成真实订单
- 执行层不需要知道上游如何推导出这个目标

备选方案：

- 继续把 `requested_budget`、`deployment_pace`、`strategic_floor_cap` 之类字段传入执行层

不采用原因：

- 会让执行内核半理解策略
- 使执行合同与研究合同混层

### 决策 4：正式审计与研究诊断分层

正式审计只保留：

- 正式订单
- 正式持仓
- 正式净值
- 正式归因

研究诊断负责：

- 缺口解释
- 诊断拆分
- 排障视图

理由：

- 正式产物必须稳定、可复现、可比较
- 研究诊断必须可扩展，但不该定义正式真相

备选方案：

- 继续在正式产物里直接堆叠研究诊断字段

不采用原因：

- 会放大正式合同漂移
- 会让前端和执行层逐步依赖研究字段

## Risks / Trade-offs

- [风险] 现有实现已经依赖部分中间字段 → 缓解：本 change 先定义边界与合同，再分阶段起实现 change
- [风险] 部分历史模块本身就是过渡层 → 缓解：在 spec 中先明确它们的正式定位，避免继续误用
- [风险] 一次性触达多个共享模块，容易变成大改 → 缓解：本 change 只定义架构与合同，不捆绑策略优化
- [风险] 正式审计与研究诊断拆层后，前端可能需要适配 → 缓解：在 runtime 与 audit spec 中明确正式字段和研究字段边界

## Migration Plan

1. 先完成架构与合同层 spec
2. 再按模块边界拆分后续实现 change
3. 优先落共享层合同，再落子系统与审计层
4. 在实现 change 中逐步替换中间字段依赖
5. 保留回退路径，避免一次性切断现有运行链

## Open Questions

- 统一目标持仓合同的最小字段集是否需要单独作为独立 capability 落 spec
- 正式审计与研究诊断最终是共享同一文件，还是拆成不同产物层级
- 研究拼接层是否只保留 research-only 标记，还是需要进一步在 API 层硬隔离
