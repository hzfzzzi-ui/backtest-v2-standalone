## Context

当前系统的强项在于回测实验链已经具备较稳定的配置、执行、产物和审计协议，但「收盘后市场状态补充」仍然停留在人工分析层。用户已经明确提出两类需求：

1. 先补一份截至 `2026-03-10` 的全 A 股市场情况。
2. 后续逐步半自动化，实现每日收盘后更新。

现有代码中已经有 `run_meta` / artifacts 体系、A 股日频流动性字段补充基础以及前端结果工作台，但没有一条专门承载市场状态的产物链。若直接把市场快照塞进当前回测 schema，会污染 baseline 可比性，也会混淆“实验结果”和“市场复盘”两种语义。

## Goals / Non-Goals

**Goals:**

- 定义一条独立的日终市场快照产物链。
- 固定 6 层字段口径：指数、风格、广度、流动性、情绪、风险。
- 保证所有计算只使用 `t` 日收盘后及历史可得数据。
- 为每个交易日输出可复现的 `market_snapshot.json` 和面向人工复盘的 `market_brief.md`。
- 在产物中保留数据源、覆盖率和告警信息，便于后续审计与 UI 展示。
- 预留后续每日自动运行与前端读取的扩展点。

**Non-Goals:**

- 首轮不把 `market_snapshot` 直接接入交易策略或回测 baseline。
- 首轮不做文本情绪、新闻 NLP、盘中数据或实时推送。
- 首轮不改现有 `run_meta.json` 主 schema，不将市场快照与回测实验产物混写。
- 首轮不实现自动调度，只提供稳定的按日期构建入口。

## Decisions

### 决策 1：市场快照走独立产物链，而不是并入回测 artifacts

- 选择：输出到 `outputs/market_snapshots/YYYY-MM-DD/`。
- 不选：把市场快照字段直接塞进 `run_meta.json` 或复用实验目录。
- 原因：
  - 避免污染回测 baseline 的可比性。
  - 市场快照的运行频率、数据源血缘、用户语义都和回测实验不同。
  - 后续更容易单独做前端页面或日终复盘入口。

### 决策 2：第一阶段只做「描述性状态快照」，不做策略接入

- 选择：先固定字段、来源、血缘和重算入口。
- 不选：一开始就把 `sentiment_score`、`breadth` 等信号接入 `baseline_V9.1`。
- 原因：
  - 当前用户需求首先是“补充市场情况”和“日更”。
  - 先把数据链、口径和审计稳定下来，再决定哪些字段值得进入策略逻辑。

### 决策 3：采用 6 层 schema，并明确分层责任

- 指数层：方向与基准趋势
- 风格层：大盘/中盘/小盘与成长/科技风格强弱
- 广度层：赚钱效应扩散程度
- 流动性层：成交热度与换手环境
- 情绪层：行为型情绪代理
- 风险层：波动、相关性、脆弱性

原因：

- 这套分层足以覆盖用户当前关注的“全 A 股股市情况”。
- 各层可以逐步扩展，不必一次把所有变量塞入单一分数。

### 决策 4：官方/一手源优先，缺失时必须显式告警

- 选择：指数层优先使用中证指数与交易所；杠杆层优先使用交易所融资融券；跨境层优先使用港交所/官方披露。
- 不选：默认静默回退到匿名第三方网页抓取且不记录来源。
- 原因：
  - 市场快照后续要支持研究与审计，数据血缘必须清晰。
  - 某些字段有发布滞后或覆盖缺口，不能假装“当天可得”。

### 决策 5：所有标准化与分位数口径必须使用滚动历史窗口

- 选择：`zscore/quantile/heat` 一律用历史滚动窗口，如 20/60/252 日。
- 不选：全样本均值、全样本标准差、全样本分位数。
- 原因：
  - 后续若这些字段进入策略或研究判断，必须保持 PIT-safe。

### 决策 6：首轮实现保留 Markdown 简报

- 选择：除 JSON 外，同步生成 `market_brief.md`。
- 原因：
  - 用户当前就有“补充市场情况”的直接阅读需求。
  - Markdown 更适合人工复盘、归档和后续自动摘要。

## Risks / Trade-offs

- [官方源覆盖不完整或发布时间滞后] → 在 `market_snapshot.json` 中显式记录 `warnings`、`source_lineage` 与 `coverage`，严禁静默补零。
- [交易所/指数公司日历不一致] → 所有层统一锚定到同一 `trade_date`，并在缺失层写 `stale_as_of`。
- [情绪层误用未来信息] → 所有滚动标准化仅使用 `t` 及历史窗口，若后续接入策略，默认只允许 `t+1` 生效。
- [与现有回测产物混淆] → 独立目录、独立 schema、独立命名空间，不改 `run_meta` 主协议。
- [初版字段过多导致维护成本高] → 首轮只实现最小 6 层字段集，复杂代理如文本情绪明确留到后续变更。

## Migration Plan

1. 新增市场快照 schema 与输出目录约定，不动现有回测产物。
2. 增加按交易日构建市场快照的后端入口，支持重跑指定日期。
3. 接入最小数据源与 6 层字段计算，输出 `market_snapshot.json` 与 `market_brief.md`。
4. 补齐测试、字段说明和告警示例。
5. 后续若需要前端展示，再以独立变更增加读取/展示层。

回滚策略：

- 若实现异常，只需停用新的市场快照构建入口，不影响现有回测、baseline 和前端实验结果链。
- 产物目录与回测目录解耦，删除 `outputs/market_snapshots/` 不会破坏回测主线。

## Open Questions

- 首轮是否纳入北向资金与融资融券的历史滞后发布处理，还是先以可得日频口径为准并标注 `stale_as_of`。
- `breadth` 和 `new high/new low` 的母体，是全 A 股、剔除 ST 后全 A 股，还是与当前主股票池共用同一可交易口径。
- 首轮前端是否需要立即展示市场快照，还是先仅输出 JSON/Markdown 产物供人工消费。
