## Context

当前后端主线同时混杂了三类历史结构：

- 多配置来源并存：`preset`、`config_id`、`runtime_config_json`、`workbench_config`、`config_path` 都可能参与一次运行。
- 多执行编排并存：现网主线虽已收敛到 `VECTOR_FAST_STRICT`，但 API、编排器和引擎内部仍保留旧分支与兼容外壳。
- 多结果真相并存：引擎先写核心 CSV，API 再补 `perf/run_meta/manifest/report.html`，前端消费面与实验目录契约并未完全锁定。

与此同时，用户已经明确把 `exp_20260308_021045840_cde0` 指定为当前后端重构的锁定基线，并要求后端任何代码变动都不能改变这次回测结果。  
因此，本 change 的核心不是“立即删除旧代码”，而是先建立一套允许安全重构的基础设施：锁定基线、逐步回归门禁、单一语义配置编译路径，以及不改变结果的兼容执行壳。

## Goals / Non-Goals

**Goals:**
- 建立以后端锁定实验为中心的基线等价性验证机制。
- 明确前端语义 `config_json` 到后端 runtime plan 的唯一编译路径。
- 建立新的后端主线兼容壳，使后续重构可以在不改变结果的前提下逐层替换旧编排。
- 把数据库访问边界固定在引擎日循环之前，为后续单日循环重构做准备。
- 在不破坏现有前端消费方式的前提下，为实验目录增加稳定的配置快照和比较产物。

**Non-Goals:**
- 本 change 不追求一次性完成整套后端重构。
- 本 change 不重写现有向量化计算核。
- 本 change 不直接清空所有旧脚本、旧入口和 research-only 代码。
- 本 change 不允许通过“容忍误差”放宽基线结果要求。

## Decisions

### D1: 将 `exp_20260308_021045840_cde0` 升格为后端重构锁定基线

后续所有触及配置解析、数据装载、引擎编排和产物写盘的改动，都必须围绕这个实验执行等价性比较。  
基线不是一个抽象 preset，也不是一份模板配置，而是一个已经落盘、可审计的完整实验目录。

原因：
- 用户已经明确指定该实验为“结果不变”的基准。
- 实验目录比单一配置文件更完整，能覆盖配置、运行元信息和产物语义。

备选方案：
- 只锁定某份配置 JSON。拒绝，因为无法覆盖结果层漂移。
- 只锁定 headline metrics。拒绝，因为交易、NAV、漏斗和配置快照仍可能静默漂移。

### D2: 新主线采用“三层配置快照”而不是直接暴露 runtime 参数

新主线把配置处理分成三层：

1. `input_config.json`：前端提交的语义配置，作为唯一输入真相。
2. `resolved_config.json`：补默认值、规范化字段、校验后的标准配置。
3. `compiled_plan.json`：仅供后端执行层消费的内部运行计划。

原因：
- 用户已经明确要求前端只负责生成语义 JSON，后端可以进一步加工。
- 三层快照可以把“输入真相”和“执行派生产物”分开，既能保持单一来源，又便于审计。

备选方案：
- 直接把前端 JSON 当作最终 runtime config。拒绝，因为后端仍需要严格校验和编译。
- 继续复用 `workbench_config/runtime_config_json` 双轨。拒绝，因为这会继续制造多真相。

### D3: 兼容阶段保留旧计算核，但只允许一条公开执行主线

foundation 阶段不直接重写现有向量引擎，而是在新命名空间下建立兼容执行壳：

`config_json -> compiler -> DataBundle -> compatibility shell -> legacy strict engine core -> stable artifacts`

公开 API 只允许通过这条主线触发回测。旧入口在迁移期只做适配，不再作为产品真相继续扩展。

原因：
- 直接重写计算核会同时引入口径变化和实现变化，无法归因。
- 用兼容壳包裹旧计算核，能先把“入口真相”和“编排真相”收敛，再逐层替换内部实现。

备选方案：
- 先删旧编排再补兼容。拒绝，因为这会立即破坏基线结果可比性。
- 保留多条公开运行路径并行验证。拒绝，因为前端和脚本最终仍会继续分叉。

### D4: 数据库访问必须在主循环前收口为 `DataBundle`

新主线要求所有数据库访问都发生在 `DataBundleBuilder` 阶段，输出只读 bundle，供引擎日循环消费。  
`DataBundle` 至少包含：

- 交易日历
- benchmark 序列
- universe 快照/动态入池依赖矩阵
- raw/adjusted OHLCV
- ST、停牌、上市天数、行业映射等交易约束
- 数据完备性与时间对齐检查摘要

原因：
- 这是防未来函数和防路径漂移的硬边界。
- 只有把数据边界固定下来，后续 9-stage 单日循环才有稳定输入。

备选方案：
- 继续允许日循环中按需查库。拒绝，因为很难证明无未来函数、无时点漂移。

### D5: foundation 阶段保持核心产物文件名与语义不变，只增不改

新主线在 foundation 阶段继续产出当前前端依赖的核心文件，例如：

- `portfolio_daily.csv`
- `portfolio_trades.csv`
- `portfolio_candidates.csv`
- `perf.json`
- `run_meta.json`
- `manifest.json`

同时允许新增：

- `input_config.json`
- `resolved_config.json`
- `compiled_plan.json`
- `baseline_compare.json`

原因：
- 用户当前前端消费方式仍依赖实验目录。
- 先保持核心文件不变，才能把重构风险聚焦在后端编排层而不是前端解析层。

备选方案：
- 一步切到全新 artifact contract。拒绝，因为会把后端重构和前端迁移耦合在一起。

### D6: 旧代码淘汰采用“冻结 -> 适配 -> 等价验证 -> 删除”的顺序

本 change 只定义淘汰门槛，不直接宣告所有旧代码立刻删除。  
删除顺序固定为：

1. 多配置源入口层
2. 多执行模式外壳
3. 结果兼容补丁层
4. research-only 策略表面与旧脚本

每一层只有在新主线已覆盖职责、并通过锁定基线比较后才允许删除。

原因：
- 这是最小风险路径。
- 这样任何结果变化都能明确定位到某一层替换，而不是“大重构后统一验收”。

## Risks / Trade-offs

- [风险] 新旧主线长期并存会增加短期复杂度  
  → Mitigation：兼容壳只允许一条公开执行路径，旧路径只保留适配职责，避免继续扩展。

- [风险] 基线回归可能因为数据库内容变化而失败，即使代码未变  
  → Mitigation：比较报告必须区分代码漂移、数据漂移和诊断字段漂移，不能把所有不一致都归因于实现错误。

- [风险] 新增配置快照和比较产物后，实验目录协议变得更大  
  → Mitigation：foundation 阶段坚持“只增不改”，并由 manifest 明确列出新增产物，避免前端误读。

- [风险] 兼容壳包裹旧计算核后，团队可能误以为重构已经完成  
  → Mitigation：tasks 中明确区分 foundation 与后续阶段，并把旧代码删除条件单列为后续工作。

## Migration Plan

1. 先建立基线等价性比较脚本与 `baseline_compare.json` 产物，不改现有运行路径。
2. 再建立前端语义 `config_json` 的严格编译器，同时保留旧请求字段作为兼容适配层。
3. 再抽出 `DataBundleBuilder`，要求所有数据库访问在日循环前完成，并与旧运行结果做等价比较。
4. 再建立兼容执行壳，把公开运行主线切换到“compiler + DataBundle + legacy core”。
5. 只有在上述路径稳定通过基线验证后，才开始分层淘汰旧入口、旧分支和结果补丁层。

回滚策略：
- 每一步都保留旧编排作为只读回退路径。
- 只要基线比较出现阻塞性漂移，即回退到前一阶段，不继续向后删除旧代码。

## Open Questions

- `baseline_compare.json` 是否需要同步纳入前端结果页，还是仅作为后端治理产物存在。
- 兼容阶段是否保留独立 `job_id`，还是直接以 `experiment_id` 作为唯一公开标识。
- `compiled_plan.json` 是否在 foundation 阶段就完整公开，还是先只公开最小执行摘要。
