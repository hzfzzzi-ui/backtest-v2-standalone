## Context

本轮全系统验证已经证明，系统级重构的主边界大体成立，但仓库仍存在三类“收口失败”问题：

1. 桌面端主工作流并未真正闭环。前端会把加载后的遗留字段直接带入 `config_json`，导致后端正式 `FrontendSemanticConfig` 校验失败，用户无法完成“加载配置 -> 改参数 -> 运行”。
2. 文档与实现存在双向漂移。一部分文档仍把事务域写成主要依赖 `outputs/*`，另一部分文档又把前端宿主切换写得比实现更靠前；实现层同时还保留 `data_role` 等过渡概念。
3. cleanup 已经做了多轮，但缺少一次把“文档漂移、主工作流和低频残留”统一纳入验收的正式闭环，所以仓库会反复出现“代码已前进、文档或 spec 还停在上一阶段”的情况。

这次 change 不再继续扩架构，而是把“审计发现”转成正式收口动作。

## Goals / Non-Goals

**Goals:**

- 修平桌面端运行链，让前端对后端提交的 `config_json` 严格符合 `FrontendSemanticConfig`。
- 让前端运行前后都只围绕“正式配置合同”工作，不再把 `asset_context`、`unified_runtime`、遗留 `data_role` 之类字段透传到主运行接口。
- 追平系统、前端、数据库文档，使其明确区分“已完成边界”和“仍处于 compat 的边界”。
- 为后续 cleanup 增加正式系统审计闭环，要求在 cleanup 批次完成后再验证主工作流、文档和残留状态。

**Non-Goals:**

- 不改研究口径，不改 baseline、信号时点、成交时点或主策略逻辑。
- 不借机重做数据库 schema 或再起新的前端壳架构。
- 不在本 change 中处理 ETF 专项活跃 change。
- 不把所有低频残留一次性删除，只收口已被审计证实的主漂移和正式审计规则。

## Decisions

### 决策 1：前端运行链以“显式裁剪”而不是“后端放宽 schema”为主

选择：
- 在桌面端 `config_workspace / run_orchestration / save_orchestration` 之间新增或复用一条“正式提交载荷构造”步骤，只保留 `FrontendSemanticConfig` 允许的字段。

原因：
- 审计已证明问题根因是前端把加载态/兼容态字段透传到了正式接口。
- 如果放宽后端 schema，只会把过渡字段重新合法化，破坏“配置唯一真相”的主原则。

备选方案：
- 放宽后端 schema 接受 `asset_context`、`unified_runtime`。  
  否决，因为这会让过渡字段重新变成正式合同。

### 决策 2：文档追平采用“如实标记当前阶段”，不把 compat 现状硬写成完成态

选择：
- 系统、前端、数据库主文档只写当前真实状态：哪些主边界已经完成，哪些仍由 compat 维持。

原因：
- 现阶段的问题不是缺文档，而是文档里混有“旧现实”和“提前宣布完成”两种漂移。
- 先把文档写实，后续 cleanup 才有清晰的退出判据。

备选方案：
- 按目标态继续写文档，不暴露 compat。  
  否决，因为这会再次掩盖当前剩余工作。

### 决策 3：系统审计闭环作为独立 capability 固化，而不是继续依赖临时人工复盘

选择：
- 新增 `system-audit-closure` capability，把三件事固定成正式审计范围：
  - 文档与实现漂移
  - 主工作流验证
  - 低频残留扫描

原因：
- cleanup 已经进入后期，仓库需要一条正式的“收口验收”路径。
- 没有这条闭环，后续很容易再次出现“功能已切换但 spec/文档/测试未追平”。

备选方案：
- 继续用一次性检查替代正式 capability。  
  否决，因为无法沉淀成长期治理规则。

## Risks / Trade-offs

- [风险] 前端配置裁剪可能误删当前 UI 仍在使用的兼容字段。  
  → 缓解：只在“提交给后端”的 payload 上裁剪，保留本地 workspace 状态中的辅助字段；并用 Playwright 回归 `加载/运行/保存`。

- [风险] 文档追平后，会暴露某些边界其实仍未完全完成。  
  → 缓解：明确区分“正式主路径已接管”和“compat 尚未退出”，避免继续提前宣布完成。

- [风险] 系统审计 capability 引入后，会增加每轮 cleanup 的验证成本。  
  → 缓解：只要求覆盖主工作流、关键文档和低频残留，不要求每次跑全仓全量回归。

- [风险] `data_role` 等过渡概念被标记为 compat 后，现有测试需要同步更新。  
  → 缓解：测试改成验证“compat 仍存在但不再是正式默认合同”，而不是继续把它当主语义。

## Migration Plan

1. 先在前端提交链增加正式 payload sanitizer，并用桌面主工作流做回归。
2. 同步更新后端/文档中与 `FrontendSemanticConfig`、`data_role`、前端宿主阶段、事务域现状相关的主说明。
3. 新增系统审计 capability 与对应 cleanup 规则。
4. 做一次最小系统复核：
   - 文档与实现是否对齐
   - `加载配置 -> 运行` 是否跑通
   - 残留对象是否从“主路径残留”降级为“低频治理项”

回退策略：
- 前端部分可回退到裁剪前的 payload 构造逻辑；
- 文档部分为纯文本回退；
- 审计 capability 为增量规则，不影响运行时行为，可单独回退。

## Open Questions

- 前端 `config_json` 裁剪逻辑最终应放在 `config-workspace`、`run-orchestration`，还是单独的共享 serializer helper 中，需结合现有桌面壳代码形态决定。
- `data_role` 在实现中还会保留多久尚未最终确定；本 change 只要求把它明确降级为 compat，而不强制彻底删除。
