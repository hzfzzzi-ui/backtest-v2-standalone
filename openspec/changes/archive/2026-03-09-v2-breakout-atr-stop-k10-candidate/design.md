## Context

锁定 baseline `exp_20260307_051743747_77d8` 后，第一轮自主探索对 `regime_ma`、entry buffer、momentum、take profit、ATR 类退出参数做了最小可证伪实验。当前唯一在全样本上同时改善 `CAGR / MaxDD / Sharpe` 的候选是 `breakout_trend` 路径下的 `strategy.params.atr_stop_k=1.0`。

已确认的约束：
- baseline 口径不可变，尤其是手续费、滑点、股票池、成交规则、评价口径与 `benchmark_regime` 语义。
- 候选优势不能只靠单个终点或少数月份解释，因此必须保留局部稳健性、分段窗口和终点敏感性证据。
- 当前系统收益高度依赖趋势持仓的期末未平仓浮盈，因此候选升级流程必须把“研究优胜”与“正式 baseline”区分开。

## Goals / Non-Goals

**Goals:**
- 为 `atr_stop_k=1.0` 建立正式候选方案，而不是直接替换当前 baseline。
- 保证候选运行时配置只允许一个主改动：`strategy.params.atr_stop_k`。
- 保证候选默认关闭，显式启用后仍能一键回退到 baseline。
- 在实现前固化候选所需审计证据，避免“结果看起来更好但无法复核”。

**Non-Goals:**
- 直接把 `atr_stop_k=1.0` 升级为新的默认 baseline。
- 改写 ATR 止损算法、手续费模型、滑点模型或执行规则。
- 扩大为多参数联动优化或新的横向参数搜索。
- 重新定义已有 `benchmark_regime`、风险预算或报告语义。

## Decisions

### D1: 候选配置以锁定 baseline 为唯一来源
实现候选时，运行时配置 SHALL 从 `exp_20260307_051743747_77d8/run_config.json` 派生，而不是从预设名、前端草稿或当前代码默认值推断。这样可以把候选限定为“对锁定 baseline 的单参数偏移”。

选择这一方案，而不直接修改代码默认值，是因为 baseline 本身已经是受合同约束的真实输入真相。若直接改默认值，会把“研究候选”与“主线默认行为”混在一起。

### D2: 候选启用必须显式，默认保持 baseline
实现候选时，应通过显式配置标记、专用实验脚本或独立 preset 启用 `atr_stop_k=1.0`；未显式启用时，系统仍使用 baseline 的 `atr_stop_k=1.2`。

选择显式启用而不静默覆盖，是为了满足“默认关闭、可回退、可审计”。研究优胜不等于默认正确。

### D3: 单路径漂移门禁
候选运行时配置需要在编译后执行 diff 门禁。除 `strategy.params.atr_stop_k` 外，若出现 `costs`、`execution`、`universe`、`benchmark`、`benchmark_regime` 或其他参数漂移，候选构建 SHALL 失败。

选择运行时 diff 门禁，而不是靠人工 review，是因为本项目当前已经存在配置源较多、历史行为较复杂的问题，人工检查不足以防止静默漂移。

### D4: 候选 readiness 依赖证据包，而不是单次回测
候选被标记为“ready for implementation”前，必须具备以下证据：
- 全样本对照结果
- `0.9 / 1.0 / 1.1` 局部稳健性
- 分段窗口检查
- 至少 3 个截断终点的终点敏感性检查
- `t` 日信号、`t+1` 执行的口径确认

选择证据包门槛，而不只看一组 headline metrics，是因为 `atr_stop_k=1.0` 的优势主要集中在弱市修复，且全系统收益受未平仓浮盈影响较大。

### D5: 回退优先于迁移
候选落地后若出现审计失败、行为争议或用户否决，回退方案仅需取消候选启用并恢复 baseline 参数，不涉及数据迁移、产物迁移或历史实验重写。

选择“轻回退”而不做迁移，是因为本次变更目标只是参数候选化，不是策略架构重构。

## Risks / Trade-offs

- [风险] `atr_stop_k=1.0` 的优势主要来自 2018-2022，最近窗口收益弹性下降。
  - 缓解：在候选结论中明确记录 `W3` 退化，不把它包装成无条件升级。
- [风险] 全系统绩效高度依赖期末未平仓趋势仓，可能放大样本终点效应。
  - 缓解：保留终点敏感性检查，且要求候选结论同时报告已实现与未实现贡献的局限性。
- [风险] 候选实现时可能被其他配置源静默覆盖。
  - 缓解：增加编译后 diff 门禁与 provenance 记录，候选不允许从模糊默认值推断。
- [风险] 用户可能将“正式候选”误解为“新 baseline 已经确定”。
  - 缓解：命名、文档和任务中明确使用 candidate 语义，禁止默认值直接切换。

## Migration Plan

1. 先实现“显式候选启用 + 单路径漂移校验”，保持 baseline 默认行为不变。
2. 基于锁定 baseline 重跑 candidate 对照，确认产物中的 provenance 与审计摘要齐全。
3. 仅在用户明确接受候选结论后，才讨论是否发起下一条“baseline promotion”变更。
4. 如任一步骤发现未来函数、时间错位或非目标参数漂移，立即停止收益优化，保留 baseline。

## Open Questions

- 正式候选要通过哪一个入口暴露更合适：专用实验脚本、显式 preset，还是前端工作台中的受控开关。
- 若未来用户决定将 `1.0` 升级为 baseline，是否需要额外增加更长样本外窗口或横向市场状态分层检查。
