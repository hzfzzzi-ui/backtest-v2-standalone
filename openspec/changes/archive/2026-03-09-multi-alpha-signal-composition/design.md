## Context

当前系统已经有统一的 9-stage 运行壳、公开单次回测主路径和基础信号提供者协议，但多策略组合仍停留在单策略特例拼接阶段。现状有 4 个关键约束：

- 运行时仍以单策略或特例路由为主，缺少通用的多 alpha 组合契约。
- 持仓状态主要按 `symbol` 聚合，缺少稳定的 `alpha`/`sleeve` 来源归因。
- `S7` 现有语义已经偏向仓位控制与订单规划，不适合继续堆叠信号启停和冲突裁决职责。
- 系统必须继续遵守 `t` 日收盘生成信号、`t+1` 日执行的交易时钟，不能因组合层引入口径漂移或时间错位。

本次设计面向 3 类直接使用者：

- 研究人员：需要把 `breakout_55`、`rsi_reversal` 等 alpha 以可比较、可归因的方式做组合实验。
- 回测审计者：需要验证组合启停、同股冲突、来源退出是否真的按规则执行。
- 前端工作台：需要消费稳定的配置协议与诊断产物，展示组合层是否生效。

## Goals / Non-Goals

**Goals:**

- 在不新增可见 stage 编号的前提下，为现有 9-stage 运行壳补充通用多 alpha 组合能力。
- 定义从原始 alpha 信号到组合信号、再到持仓与退出的来源归因链路。
- 让前端配置可以编译为运行时组合配置，并保持 baseline 默认行为不变。
- 为组合决策提供最小可观测产物，包括启停、冲突裁决、sleeve 预算和来源感知退出统计。
- 第一阶段仅支持 `breakout_55 + rsi_reversal`，组合模式仅支持 `regime_route`，仓位模式仅支持 `hard_sleeve_budget`。

**Non-Goals:**

- 不新增第 10 个 stage，也不修改当前 UI 的 9-stage 展示口径。
- 不在第一阶段支持任意数量 alpha 的统一归一化排序，也不引入 `unified_rank`。
- 不在第一阶段支持跨来源 partial exit、自动净额合仓或自适应权重学习。
- 不改变现有交易时钟、成交假设、baseline 成本口径、股票池口径和风险统计口径。

## Decisions

### 决策 1：保留 9-stage 口径，把组合层定义为 `S6` 的内部子层

设计采用以下语义：

- `S6a`：多 alpha 原始信号生成
- `S6b`：多 alpha 信号组合
- `S7`：仓位控制与订单规划
- `S8`：组合级风险控制
- `S9`：来源感知退出

原因：

- 当前 `S7` 已承担仓位控制和订单规划语义，若再承担 alpha 启停与冲突裁决，会导致收益归因混乱。
- 当前 UI 和研究语境已经接受 9-stage 编号，新增可见 stage 会带来协议与展示同步成本。
- 组合层本质仍属于“入场前的信号决策”，而不是“持仓后的仓位控制”。

备选方案：

- 新增一个可见的 `S7` 信号组合层：放弃。会破坏现有 9-stage 协议和前后端语义一致性。
- 把组合逻辑全部塞进现有 `S7`：放弃。会把 alpha 决策与仓位构建混成一个黑盒。

### 决策 2：引入两段式信号契约 `raw_alpha_signal -> composed_signal`

第一阶段统一引入两类信号对象：

- `raw_alpha_signal`
  - 来自各 alpha 模块的原始买卖意图
  - 必须带 `alpha_id`、`alpha_family`、`symbol`、`side`、`raw_score`、`reason_code`
- `composed_signal`
  - 来自 `S6b` 的组合结果
  - 必须带 `alpha_id`、`sleeve_id`、`compose_score`、`compose_rank`、`regime_tag`、`conflict_resolution`

原因：

- 当前扁平 `buy_signals/sell_signals` 结构不足以表达“原始信号”和“组合后信号”的区别。
- 审计需要区分“alpha 产出了什么”和“组合层最终放行了什么”。
- 统一信号契约后，后续新增 alpha 模块不需要改动组合层接口。

备选方案：

- 继续复用现有扁平信号列表，仅在 `meta` 中塞更多字段：放弃。字段语义不清晰，诊断和 spec 都难以约束。

### 决策 3：持仓必须显式带来源归因，`S9` 默认采用 `source_only` 退出所有权

第一阶段持仓与订单链路新增以下最小归因字段：

- `entry_alpha_id`
- `entry_sleeve_id`
- `entry_reason_code`
- `entry_date`

退出规则默认采用：

- `S9`: `source_only`
- `S8`: 允许 `global_risk_override`

原因：

- 如果持仓仍只有符号级状态，就无法确定某个卖出信号应不应该处理当前仓位。
- 组合研究必须能回答“这个仓位是谁开的、谁负责退出、被谁强制覆盖”。
- `S8` 保留全局风控覆盖，可以继续表达停损、熔断和组合级强平，而不污染 alpha 退出统计。

备选方案：

- 继续保留纯符号级持仓，并按最近一次信号推断来源：放弃。该方案不稳定，也无法审计。
- 让所有来源都能直接卖出同一仓位：放弃。第一阶段会显著污染研究归因。

### 决策 4：第一阶段只实现 `regime_route + hard_sleeve_budget`

第一阶段组合模式限定为：

- `compose_mode = regime_route`
- `portfolio_mode = hard_sleeve_budget`
- `same_symbol_policy = prefer_higher_score`

原因：

- `regime_route` 与现有 `S2-S4` 市场环境链路天然兼容，最容易保持经济逻辑与可审计性。
- `hard_sleeve_budget` 的预算边界明确，便于判断收益来自信号还是分仓。
- `prefer_higher_score` 提供确定性的同股冲突裁决，避免依赖遍历顺序。

备选方案：

- `sleeve_fixed` 作为第一阶段主模式：暂缓。虽然也可审计，但不直接利用已有 regime 结构。
- `unified_rank`：放弃。跨 alpha 分数归一化风险最高，容易引入口径漂移。

### 决策 5：组合配置仍走现有编译链路，新增独立配置块而不改 baseline 默认值

前端到后端的配置协议新增两块：

- `signal_generation.modules`
- `signal_composition`

并要求：

- 默认关闭新增组合逻辑
- baseline 配置不改写
- 未声明组合配置时，系统行为与当前单策略路径保持一致

原因：

- 本项目强调“配置唯一真相”，多 alpha 组合不能绕过语义编译器直接塞运行时对象。
- baseline 必须可随时复现，新增能力必须是显式启用而不是隐式接管。

备选方案：

- 直接在运行时手工拼装 alpha 列表：放弃。会造成前后端字段漂移，不利于产品化。

### 决策 6：诊断与审计产物按“组合前/组合后/持仓退出”三层输出

第一阶段新增的最小可观测信息分为三层：

- 组合前
  - 原始 alpha 信号数
  - 各 `alpha_id` 的 `reason_code` 汇总
- 组合后
  - 被启用/被抑制的 alpha 数量
  - 同股冲突裁决结果
  - sleeve 预算命中统计
- 持仓退出
  - 来源感知退出次数
  - 全局风控覆盖次数
  - 被覆盖的来源分布

原因：

- 这能最小化回答“信号是否产生”“组合是否生效”“退出是否按来源执行”三个关键问题。
- UI 和审计报告可以基于同一批字段校验策略行为，而不是依赖日志人工推断。

备选方案：

- 只输出最终订单和成交：放弃。无法验证组合层本身是否按预期生效。

## Risks / Trade-offs

- [风险] 持仓来源归因需要修改持仓状态或其旁路元数据结构，可能影响订单规划与退出逻辑的一致性  
  → 缓解：第一阶段仅新增最小归因字段，保留现有持仓核心计算口径不变，通过附加元数据逐步接入。

- [风险] `breakout_55` 与 `rsi_reversal` 的分数不可直接比较，若过早统一排序会污染实验  
  → 缓解：第一阶段禁止 `unified_rank`，只做 `regime_route` 和硬预算分仓。

- [风险] 组合层可能被误用为新的择时层，导致与 `S2-S4` 责任重叠  
  → 缓解：在 spec 中明确 `S6b` 只消费 `S2-S5` 已产出的上下文，不重新计算市场环境。

- [风险] 组合诊断产物过多会增加维护成本和 UI 适配成本  
  → 缓解：第一阶段只增加最小必需字段，优先复用既有 `reason_code`、`funnel`、`run_meta` 协议。

- [风险] 保持 baseline 兼容会让运行时出现单策略路径和组合路径并存  
  → 缓解：以显式配置切换路径，baseline 继续走原有单策略语义，组合模式只在声明后启用。

## Migration Plan

1. 先定义并冻结组合契约与来源归因 spec，不做代码层大范围改写。
2. 在配置编译链路中引入 `signal_generation.modules` 与 `signal_composition`，默认关闭。
3. 在运行时接入 `S6a`/`S6b` 的对象流转，并为订单与持仓补充来源归因字段。
4. 在 `S7`/`S9` 中接通硬预算与来源感知退出。
5. 补齐最小诊断产物与 reason_code 汇总，确保 UI 与审计可验证。
6. 以 `breakout_55 + rsi_reversal` 为唯一第一阶段组合样例验证行为。

回滚策略：

- 关闭新增组合配置即可回退到 baseline 单策略路径。
- 若运行时组合链路不稳定，可先保留归因字段和诊断输出，禁用 `S6b` 的组合放行。

## Open Questions

- 第一阶段的 `sleeve_id` 是否直接按 `trend`/`mean_revert` 固定，还是允许配置层显式命名。
- 组合后的卖出信号是否也需要单独的 `composed_signal` 对象，还是只对买入侧做组合、卖出侧保持来源直连。
- 现有持仓状态更适合扩展为内联归因字段，还是增加独立的持仓归因 sidecar 结构。
- UI 第一阶段是否只展示组合统计汇总，还是同时展示按 `alpha_id` 拆分的调试明细。
