# AGENTS.md

## 1. 目录定位

`frontend` 是本项目的**展示与交互层**。

这一层负责：

- 桌面端研究工作台
- 移动端摘要与行动清单
- 结果展示
- 交互流程
- UI 状态管理
- 前后端联动壳层

前端不是研究引擎，不是配置中枢，也不是执行逻辑主判断层。

---

## 2. 本层的核心原则

### 2.1 前端不得重算核心研究逻辑
前端不得在浏览器端重算以下内容：

- risk-on / neutral / risk-off
- 市场强弱评分
- 核心排序结果
- 主仓位决策
- 防守层目标分配
- 行动清单主结论

前端可以做的只包括：

- 展示
- 过滤
- 排序显示
- 本地 UI 状态控制
- 轻度派生展示字段
- 交互确认与回传

换句话说：

**前端消费研究层 / 后端提供的结构化结果，不在前端重新发明一套“决策引擎”。**

### 2.2 桌面端与移动端分工不同
前端默认分工是：

- **桌面端**：研究工作台，信息密度更高，偏分析、复盘、配置查看与结果操作
- **移动端**：每日摘要、行动清单、状态提醒、轻确认

不要把移动端做成桌面端缩小版，也不要把桌面端做成只会显示几个卡片的弱壳。

### 2.3 旧壳文件是过渡层
以下文件当前视为过渡层 / 兼容层：

- `frontend/assets/js/backtest_v2.js`
- `frontend/assets/js/ui-controls.js`
- `frontend/assets/js/artifacts.js`

这些文件允许维护，但不应继续承接新的长期主逻辑。

新增主逻辑应优先进入更清晰的前端主路径，例如：

- `frontend/app/results-workbench/`
- `components`
- `composables`
- `helpers`
- `state`

### 2.4 桌面端与移动端必须消费统一 action schema
桌面端和移动端必须消费同一套后端 / 研究层输出的结构化 action schema。

不允许为了某一端展示方便，各自私下定义一套“相似但不同”的动作对象。

这条规则对未来每日行动清单闭环是强约束。

---

## 3. 允许做什么

在本目录中，允许且鼓励做的事情包括：

- 页面重组
- 展示层瘦身
- 组件拆分
- 状态管理整理
- 交互流程优化
- 统一 schema 消费方式
- 提高桌面端 / 移动端信息分工清晰度
- 提高可维护性和可读性

如果目标是：

- 让前端更清楚地展示研究结论
- 让 action object 更稳定地被消费
- 让桌面端 / 移动端职责更清晰

通常是值得推进的。

---

## 4. 禁止事项

你不得：

- 在前端重算核心研究逻辑
- 为了展示方便，在前端偷偷重写 action 结论
- 让桌面端和移动端消费不同 schema
- 继续把新的长期逻辑堆进旧壳文件
- 为了赶进度，把本应在 backend/research 或 backend/core 决定的内容搬到前端判断
- 让 UI 需求反向污染研究口径

---

## 5. 修改本层后的输出要求

凡是非微小改动，默认都必须说明：

1. 改动影响桌面端、移动端，还是共享层  
2. 是否引入了新的 schema 依赖  
3. 是否改变了 action object 的消费方式  
4. 是否仍然遵守“前端不重算核心逻辑”  
5. 是否把过渡层逻辑向正式主路径收口  
6. 如何验证页面行为与数据一致性  

如果涉及旧壳文件，还必须说明：

- 为什么这次仍需改旧壳
- 是否有计划后续把逻辑迁入正式主路径

---

## 6. 默认工作方式

在 `frontend` 下工作时，默认遵循：

- 先区分桌面端与移动端目标，再设计页面
- 先确认数据 schema，再写展示逻辑
- 优先把新逻辑放进正式主路径
- 优先瘦旧壳，而不是继续给旧壳加业务
- 把前端当“结果工作台”，而不是“研究替代引擎”
