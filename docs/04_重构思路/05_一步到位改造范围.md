# 05_一步到位改造范围

## 1. 结论

如果一步到位把当前系统改造成“账户配置中枢 V2”，这是一次明确的 `L3+` 大改。

它不是单点优化，而是同时改：

- 顶层真相
- 预算分配
- 弱势处理语义
- ETF 角色分工
- 状态切换时的现金释放
- explain / audit / frontend 展示

工程上能做，但不建议直接一轮完成。

原因不是代码写不出来，而是：

- 架构变化
- 策略行为变化
- 回测结果变化

会被绑在同一轮里，后续很难归因。

---

## 2. 一步到位要改什么

### 2.1 顶层从组合装配升级为账户配置中枢

当前主线更像：

- `stock sleeve`
- `ETF sleeve`
- `50/50 combo`

一步到位后，顶层应改为：

- `Account Allocator`
- `Defense budget`
- `Core beta budget`
- `Alpha budget`

也就是：

先由账户层决定整个账户该持有什么，再把预算下发给 sleeves。

### 2.2 ETF 不再作为万能腿存在

ETF 在一步到位方案里，至少要在语义上拆成：

- `Defense`
- `Core Beta`

即使第一版不立刻拆成两个独立 runtime sleeve，也必须拆成：

- 两种 budget
- 两种 explain
- 两种状态角色

### 2.3 状态切换时现金释放上收到账户层

进入 `RISK_OFF / TRANS_DOWN` 时，系统需要先回答：

- 哪些旧仓允许 carry
- 哪些旧仓应减仓
- 释放多少现金给 defense / accumulation

否则 target 再合理，也会继续因为现金碎片与库存惯性而落不下去。

### 2.4 执行可行性必须提前进入预算合同

一步到位架构不能再接受：

- target 看起来合理
- explain 看起来正确
- live 行为完全被 lot / cash / rebalance 门槛否决

执行现实必须在更高层被显式考虑。

---

## 3. 预计改动范围

### 3.1 后端核心主线

大概率会改到：

- `backend/api/backtest_v2`
- `backend/core/services`
- `backend/core/config/etf_beta`
- `backend/core/engine_vector/etf_beta`
- `backend/core/portfolio`
- `backend/core/stage_pipeline/adapters`
- `backend/core/audit`

### 3.2 前端 explain / 结果工作台

大概率会改到：

- `frontend/assets/js/desktop-shell`
- `frontend/app/results-workbench`

因为前端不再只展示：

- stock sleeve
- ETF sleeve

而要展示：

- 账户预算
- defense/core/alpha 预算分配
- 状态切换与现金释放的账户级解释

### 3.3 合同与文档

必改：

- `openspec/specs`
- `docs/01_系统接口模块定义`
- `docs/02_系统架构设计`
- `docs/04_重构思路`

### 3.4 回归与验收

必改：

- `tests/unit`
- `tests/frontend`
- 最小正式回归入口
- baseline replay 验收口径

---

## 4. 预计改动量

这是一次高强度结构性改造。

保守估计：

- 核心源码改动：`18-30` 个文件
- spec / docs / tests 同步：`15-25` 个文件
- 总文件量：`35-55` 个文件
- 新增 / 重写代码量：约 `2500-5000` 行

真正的难点不是代码量，而是行为归因。

---

## 5. 一步到位的四个必改能力

如果真要一步到位，至少要把下面四个能力写进同一套设计里。

### 5.1 Account Allocator

账户级唯一真相，输出：

- defense budget
- core beta budget
- alpha budget
- 状态切换动作

### 5.2 State-edge cash release

状态切换时显式释放现金，不再把现金来源留给 execution path 自己解决。

### 5.3 Defense / Core Beta 显式分桶

ETF 不再只是一条混合腿，而要至少在预算与 explain 上拆出：

- 防守桶
- 核心 beta 桶

### 5.4 Execution feasibility integrated with budget

lot、现金、最小成交单位、再平衡频率，要和预算设计一起考虑。

---

## 6. 一步到位明确不建议同时做的事

即便一步到位，也不建议再额外绑定这些变化：

- 重写 stock alpha 因子
- 改 benchmark / regime 定义
- 新增更多资产类别
- 把弱势左侧推广到个股
- 同时追求更高 CAGR 与更低换手

否则这轮会彻底失去可归因性。

---

## 7. 主要风险

### 7.1 行为变化无法归因

这是最大风险。

因为一旦：

- 预算变了
- ETF 角色变了
- 现金释放逻辑变了
- execution feasibility 变了

最终看到的 `Sharpe / MaxDD / CAGR` 变化就很难拆解来源。

### 7.2 账户层变成更复杂的新补丁层

账户层应更强，但不能更乱。

如果做完之后：

- explain 更复杂
- 预算更难懂
- 行为更难预测

那这轮重构就是失败。

### 7.3 过早拆成太多 runtime sleeve

先拆语义，不一定先拆代码。

否则工程噪音会压过研究价值。

---

## 8. 当前建议

如果目标是稳定推进，不建议直接一步到位。

更合理的做法是：

1. 先做 `Account Allocator Shadow Mode`
2. 再让账户层接管预算
3. 再拆 ETF 的 defense / core beta 语义
4. 最后再决定是否正式切成账户配置系统

一句话：

**一步到位是理论可行的，但对当前主线来说，分阶段迁移更符合可审计、可解释、可回滚的研发纪律。**
