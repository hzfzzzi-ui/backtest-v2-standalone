# 数据库架构设计

## 0. 文档定位

本文档是当前仓库数据库层的正式主文档，优先回答：

- 数据库正式覆盖哪些范围
- 数据库的正式职责是什么
- 市场数据域、业务事务域、实验域如何分层
- `outputs/` 与数据库的边界是什么
- 当前实现相对目标架构还偏移在哪里

表级 schema contract、runbook、apply SQL 和专项治理文档，均从属于本文档，不再单独承担数据库总架构定义职责。

## 1. 正式职责

数据库当前同时承担两类正式职责：

1. 研究数据真相层
2. 系统运营真相层

这意味着数据库既要支撑：

- A 股研究数据
- 后续扩展到美股的 L1 / L2 数据
- 交易事务
- 账户与持仓同步
- 实验元数据与审计摘要

但数据库不承担：

- 前端展示真相
- 运行产物目录真相
- 研究解释文案真相

## 2. 正式边界

### 2.1 `outputs/` 边界

`outputs/` 继续定义为数据库外部产物层。

正式原则：

- `outputs/` 可以保存实验产物、明细文件、报表和临时运行输出
- `outputs/` 不是数据库真相层
- 不允许把本应落入数据库主域的长期真相对象继续沉淀为文件主路径

### 2.2 `runtime compat` 边界

`runtime compat` 不再作为数据库正式长期层保留。

当前仍存在的 runtime compatibility view / adapter / access path，只能视为过渡实现，后续应尽量被：

- `canonical_market`
- 或统一数据访问层

吸收，不应继续长成独立长期主层。

## 3. 正式分域

数据库正式上收敛为 3 个域：

1. 市场数据域
2. 业务事务域
3. 实验域

其中：

- 市场数据域优先服务研究、回测、审计真相
- 业务事务域优先服务账户、交易、同步、执行真相
- 实验域优先服务实验索引、配置引用和审计摘要

长期方向上，研究数据域与业务事务域应拆为不同物理库；当前实现可以暂时共库，但必须保持逻辑域隔离。

## 4. 市场数据域

### 4.1 正式目标

市场数据域默认采用 PIT 口径，不再把原始源表直接视为正式消费层。

正式主路径固定为 3 层：

1. `raw_source`
2. `pit_mapping`
3. `canonical_market`

研究 / 回测正式上默认只消费 `canonical_market`，不再把：

- `v1`
- `v2_runtime`

作为并列正式 data role 暴露给上层。

### 4.2 `raw_source`

职责：

- 保留原始抓取事实
- 保留源表可追溯性
- 不直接承担正式研究消费真相

当前典型对象包括：

- `raw_tushare_daily`
- `raw_tushare_adj_factor`
- `raw_tushare_daily_basic`
- `raw_tushare_suspend_d`
- `raw_tushare_stk_limit`
- `raw_tushare_moneyflow`

### 4.3 `pit_mapping`

职责：

- 处理时点映射
- 处理证券谱系
- 处理市场阶段切换
- 处理指数成分、行业归属和历史有效期

当前典型对象包括：

- `pit_security_symbol_lineage`
- `pit_index_constituents`
- `pit_industry_history`
- `pit_security_master`
- `pit_st_history`
- `pit_trade_cal`

### 4.4 `canonical_market`

职责：

- 形成正式可消费市场真相
- 吸收原始源、PIT 映射和构建审计规则
- 提供统一研究消费入口

当前典型对象包括：

- `pams_ohlcv_daily_v2`
- `pit_index_daily`
- `pit_stock_moneyflow_v2`
- `pams_ohlcv_daily_v2_audit_daily`
- `pams_ohlcv_daily_v2_exceptions`

### 4.5 当前约束

当前市场数据域的正式原则是：

- `canonical_market` 才是正式市场真相
- `raw_source` 不对研究层直接暴露为正式消费入口
- `runtime compat` 只能是过渡访问形态，不再视为正式层级
- `data_role` 不再作为长期正式配置概念保留；当前仅允许作为迁移期内部字段存在，长期应被更稳定的市场数据访问合同替代
- `pams_ohlcv_daily` 只保留为历史参考与迁移对象，长期目标是完全退役，不再作为正式默认主路径

### 4.6 正式访问边界

市场数据域的正式访问边界应收敛为统一的 market data access contract。

正式原则：

- 应用主路径不得再直接 `psycopg.connect` 查询市场数据表
- 价格、指数、行业、PIT 成分、交易日历等访问，都必须经过统一市场数据访问层
- `data_role / stocks_table / stocks_mapping_table` 这类表级切换开关，不应继续作为长期上层合同

统一市场数据访问层当前最小正式能力至少包括：

- 价格历史
- benchmark 历史
- 交易日历
- PIT 成分
- PIT 行业
- 证券主数据

这些能力应按业务能力命名，而不是按底表命名。

当前固定输入维度至少包括：

- `asset_scope`
- `market`
- `data_level`
- `as_of_date` 或 `window`
- `symbols`

当前固定审计回显至少包括：

- 实际命中的 canonical 对象
- 时间窗口
- 市场
- 是否降级
- 是否缺数
- 查询版本
- `cache_hit`
- `cache_version`

查询形态当前收敛为：

- `价格历史`：单标的与批量都支持
- `证券主数据`：单标的与批量都支持
- `benchmark 历史`：单标的与批量都支持，合同层不再区分指数接口与 ETF 接口
- `PIT 成分`：同时保留 `as_of_date` 快照与 `window` 历史切片，快照是主能力
- `PIT 行业`：同时保留 `as_of_date` 快照与 `window` 历史切片，快照是主能力
- `交易日历`：只保留批量能力，并只承诺最小口径

最小正式返回字段当前建议收敛为：

- `价格历史 / benchmark 历史`：`date / symbol / open / high / low / close / volume / amount / adj_factor / is_suspended`
- `PIT 成分`：`index_code / symbol / start_date / end_date / as_of_date`
- `PIT 行业`：`symbol / industry_l1 / industry_l2 / standard / start_date / end_date / as_of_date`
- `证券主数据`：`symbol / ts_code / name / market / exchange / security_type / asset_scope / list_date / delist_date / is_active_at_asof`

其中：

- `benchmark 历史` 复用 `价格历史` 的同一输出结构
- `name` 与 `asset_scope` 已提升为证券主数据必返字段
- 交易日历当前只承诺最小口径：交易日序列、`is_trading_day`、`calendar_version`

缓存语义当前建议收敛为：

- `cache_hit` 必返
- `cache_version` 必返
- 直接命中 canonical 时固定返回 `cache_hit = false` 与 `cache_version = "direct_canonical"`

统一市场数据访问层最终应同时覆盖：

- 价格序列访问
- benchmark 访问
- PIT 指数成分访问
- PIT 行业历史访问
- 交易日历访问
- 跨市场 schema 映射

### 4.7 跨市场骨架

市场数据域从正式文档层面，当前就应预留跨市场统一骨架。

建议骨架：

1. `CN_A_L1 canonical`
2. `US_L1 canonical`
3. `cross_market_access_contract`

其中：

- `L1 canonical` 负责标准日频或基础行情真相
- `cross_market_access_contract` 负责跨市场统一访问语义，而不是要求不同市场共享同一张表

当前不把 `L2 canonical` 纳入正式范围；未来如接入 `L2` 数据，应作为统一访问合同下的独立扩展，而不是提前在正式文档里把空层写成已落地能力。

当前阶段只要求先把这层骨架写进文档，不要求一次性落实现。

## 5. 业务事务域

### 5.1 正式目标

业务事务域承载账户、持仓、交易、现金与同步运营真相。

正式上应至少包括以下对象：

- 账户主数据
- 当前持仓快照
- 交易 / 成交真相
- 账户运营日志
- 现金账本
- 同步 / 对账日志

### 5.2 `transactions` 主对象

`transactions` 的正式目标不是一张薄记账表，而是一条完整交易生命周期主表。

它应覆盖的生命周期至少包括：

- 审批
- 提交
- 成交
- 拒绝
- 撤销

这意味着当前分散在：

- `approval_tickets`
- `execution_events`

中的长期真相，目标上应统一并入事务域数据库，由 `transactions` 主对象承接，而不是继续长期存放在 `outputs/mobile_ops/*`。

当前实现阶段已进入：

- DB 主读写
- 文件 shadow write / compat fallback

也就是说，`outputs/mobile_ops/*` 已不再是正式主真相路径；它们当前只允许作为迁移期回退、审计对照或历史兼容产物存在。

### 5.3 账户运营子域

模拟账户及其现金账本、持仓快照、同步与对账功能已从本副本移除；代码不再创建或访问相应模拟账户表。此代码清理不代表已对生产数据库执行删表。

交易生命周期表和行情同步所需表、字段必须预先存在：运行时只读检查 schema，不自动建表、加列或建索引。生命周期表缺失时写接口及独立生命周期查询返回明确不可用错误，票据及执行事件的写入前进行预检；只读 dashboard 保留研究和行情信息，交易状态及数量显示未知。行情同步表或字段缺失时对应作业失败。数据库连接不可用仍沿用原有文件兼容降级。部署前须另行只读确认实际 schema，迁移和删表均不随本次代码部署自动执行。

### 5.4 `reconcile` 的正式定位

`reconcile` 不定义为事务域底层真相对象。

如未来重新设计账户对账，目标定位是（本副本当前不提供此能力）：

- 基于账户状态与最新研究结果生成的衍生分析结果
- 数据库只保留摘要、引用或索引
- 不把完整 `reconcile payload` 升格为业务事务域主真相

### 5.5 当前不纳入范围

`notifications` 当前不纳入数据库正式范围。

如果未来引入，也应作为明确的事务域对象追加，而不是继续以文件 feed 形式长期存在。

## 6. 实验域

### 6.1 正式目标

实验域用于保存实验级元数据、引用关系和审计摘要，不等于把整个实验产物目录搬进数据库。

正式上先收敛为以下对象：

- experiment metadata
- config refs
- baseline refs
- audit / exception summaries
- runtime snapshot 索引

### 6.2 与 `outputs/experiments` 的边界

当前正式原则：

- 详细大产物继续保留在 `outputs/experiments/*`
- 数据库只保存实验级索引、引用和摘要
- 数据库不直接承载全部实验明细文件

这条边界同样适用于：

- `manifest`
- `audit`
- `compare`
- `runtime snapshot`

数据库可以保存这些对象的元数据与引用，但不要求把详细 payload 全量搬入数据库。

## 7. 当前实现偏移

当前实现相对目标架构，至少存在以下偏移：

1. 表太散，研究数据、事务数据与实验数据没有清晰总入口
2. 口径不清，`canonical`、runtime compat、文件产物边界仍会混用
3. 直接 SQL 接入过散，数据库访问层没有统一边界
4. `data_role`、`stocks_table` 一类迁移期字段仍在少数编译/审计路径中存活，尚未完全退出上层实现
5. 事务域已进入 DB 主读写 + compat 回退阶段，但 file-backed shadow write 仍未彻底退出
6. 研究库与业务库当前仍未物理拆分

这些偏移说明当前数据库文档收口的重点不是继续加更多专项脚本，而是先固化域边界与真相归属。

1. 本文档：数据库总架构与边界
2. `市场数据访问边界.md`：市场数据正式访问边界
3. `历史行情日表v2结构合同.md`：A 股 canonical 市场主表 contract
4. `v2字段来源矩阵.md`：V2 主源 / 补源 / 审计源矩阵
5. `历史行情日表v2运行合同.md`：当前过渡期 runtime compatibility contract
6. 各类 runbook / apply SQL：仅描述具体实施，不再承担总架构定义职责
