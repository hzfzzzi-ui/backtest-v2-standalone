# 研究工作台前端瘦身审计

## 结论

下一轮前端清理应优先处理 `frontend/app/results-workbench/helpers/resultsFormatting.js`，而不是 desktop bridge。bridge 文件较小，主要负责状态交接；`resultsFormatting.js` 混合了多类职责，是后续口径漂移风险最高的位置。

## 当前职责

`resultsFormatting.js` 当前同时承担：

- 基础展示格式化：数字、百分比、金额、比率。
- 仅用于展示的 NAV 统计：滚动 Sharpe、Sortino、alpha/beta、回撤持续时间。
- 交易行与证券行的展示归一。
- 组合组件和执行合同说明。
- 运行元数据和策略展示字段。
- 委托给 agent 与 stage funnel helper 的报告格式化。

单独阅读这个文件仍然可理解，但从长期边界看较弱：新的 UI 工作很容易继续向这里加入后端口径类逻辑。

## 边界规则

前端 helper 可以从已经加载的 artifact 中派生轻量展示提示。前端 helper 不得成为 CAGR、最大回撤、交易规则、执行真相、账户 NAV、study verdict 或 baseline comparison 的 canonical source。

凡是会影响研究解释、baseline 升级或审计判断的值，都应先由后端 artifact 或 study output 生成，前端只负责渲染。

## 可拆分候选

1. `displayFormatPrimitives.js`
   - 负责 `fmtNum`、`fmtPct`、`fmtInt`、`fmtMoney`、`fmtRatio`、`firstDefined`。
   - 风险低，容易测试。

2. `displayNavStats.js`
   - 负责 `buildDatedReturns`、`latestRollingSharpe`、`alphaBeta`、回撤持续时间展示 helper。
   - 必须明确记录为仅展示用途。
   - 不得用于审计或 baseline comparison。

3. `comboContractFormatting.js`
   - 负责组合组件来源、执行合同、运行时 flag 和策略字段文本提取。
   - 这是合同展示逻辑，不是图表或指标逻辑，适合先拆。

4. `symbolPerformanceFormatting.js`
   - 负责证券行归一、已实现盈亏展示统计和 top-N 展示 helper。
   - 应渲染后端 `symbol_performance` artifact，不得发明 canonical PnL。

## 暂缓事项

- `frontend/assets/js/desktop-shell/results-workspace.js`：暂时保留。它主要负责 snapshot store 和 surface hydration。
- `frontend/assets/js/charts.js`：等图表 adapter 工作恢复后再拆。
- `frontend/assets/css/workbench.css`：等视觉系统专项再处理；没有截图验证时，CSS 清理容易过度。

## 建议第一刀

先拆 `displayFormatPrimitives.js`。它行为风险最低，可以为后续拆分建立模式。随后再拆 `comboContractFormatting.js`，因为它能在不触碰指标的前提下降低概念负担。

## 验证

- 对被修改的 JS 模块做语法检查。
- 如果页面已启动，执行现有前端 smoke 或浏览器检查。
- 除非 API 合同变化，否则不要求后端测试。
